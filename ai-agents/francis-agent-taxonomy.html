A capability taxonomy for Francis agents

Worked backwards from 20 user prompts to create unifying tools. The taxonomy follows from seven principles.

PrincipleWhat it means
Agentic retrieval, never the whole modelThe agent pulls the small slice each task needs, on demand. The full model is never handed to the LLM.
Defaults come from the caller's contextWhen the user prompts from inside a model, sheet, or date range, that location is attached as context and becomes the default model, sheet, source, and period a tool reads. With no such context, the agent falls back to a sensible default or asks — so the tool inputs below don't restate per-field defaults.
Reads return a bounded sliceAny read over a large collection — accounts, journal entries, ranked results — returns counts plus a capped, paged slice, never the full set, regardless of filter state.
The engine computes; the LLM narratesReconciliation, variance, and integrity checks are deterministic engine work. The LLM navigates, explains, and proposes — it never does the arithmetic itself.
Writes default to suggestionsModel changes are proposed for a human to approve — by default the commit path contains no AI. A trusted operator can opt a session into direct-edit mode (set up front, not per call), where changes commit immediately with no approval; it's off by default and audit-logged.
Comments are a direct writeThey annotate rather than change numbers, so they take effect immediately instead of going through the suggestion queue.
Permissions mirror the userThe agent can do only what the calling user can.

00 / How to read this

The classification system

Two orthogonal axes describe every tool. What it does to state (read, suggest, write) and who computes (the engine returns numbers; the LLM narrates them). A build-status tag marks each tool active or planned.

Effect on state

  • readRead. Retrieves state, changing nothing. Honors a basis argument: committed, or with a pending bundle applied.
  • suggestSuggest. Proposes a model change a human approves before it commits. Two tools by payload: values and structure.
  • writeWrite. Changes state immediately, no approval step. Covers direct edits to the model (gated, off by default) and comments (annotations that touch no model number).

Build status

  • activeActive. Built and callable today.
  • plannedPlanned. Net-new capability, not yet built.

Who computes

  • engineEngine. Deterministic. Reconciliation, variance, dependency resolution, statement checks. Returns a narrow slice — never the whole model.
  • llmLLM-side. The model decides what to call, sequences calls, and turns the returned slice into prose, commentary, or a proposed structure.

Committed vs. suggested edits (a git model)

  • committedReads the real, merged model — git's main, what's actually committed.
  • pending(bundleId)Reads the model as if that bundle of suggestions — an unmerged branch — were applied. Lets the agent verify its own proposal before handoff: ask the engine whether the BS still balances and the CF still ties, then present only a checked suggestion. The central engineering requirement — see §04.

01 / The capabilities

Five families, eighteen tools

The union of every call the 20 prompts demand. Named in Francis terms.

Retrieval & navigation

agentic context

The agent has no pre-stuffed model; it pulls exactly the slice a prompt needs. Reads of model state — structure, values, formulas — take a basis (committed or pending). Connection, journal-entry, and source lookups read committed reality only, since pending suggestions don't change them. Tools tagged bounded return counts plus a capped, paged slice of a potentially large collection rather than the full set.

list_data_sources
readengineactive

Enumerate the workspace's accounting connections: provider, entity name, last sync date, staleness state (the yellow→red card), and the latest run of integration status checks.

in
workspace
out
per source: provider, entity name, sync timestamp + staleness, status-check results, failure reason if broken
get_model_tree
readengineboundedactive

The structural map of one model: the nested hierarchy of roll-ups, breakdown roll-ups, and sheets, with each sheet's assignment (the data source bound to an entity sheet, a count of dimension values — e.g. "18 departments" — on a dimension sheet, or none), and the model timeline (range and last close; per-source forecast start lives in list_sources). Structure can differ across sources, so the map is read for a specific source. The hierarchy is human-curated and so human-scale, and is returned whole — but each sheet's assignment is summarized as a count, not an enumerated value list. Expand a sheet to page its actual dimension values (a catch-all "other" sheet can hold dozens), or scope to a sub-tree for an unusually large model.

in
model; source; optional scope (a sub-tree) or sheet to expand; basis; page cursor
out
the roll-up / sheet hierarchy with each node's role and assignment summary (the bound data source, a dimension-value count, or none); any unassigned values; the model timeline (range, last close); source list pointer. Expanding a sheet returns its assigned dimension values as a capped, paged list.
get_components
readengineboundedactive

Within a sheet: the sections, groups, rows and calculations, with each one's GL mappings, row/calc descriptions, and To-do/In-progress/Done status.

in
sheet (or subsheet); source; basis; page cursor
out
a capped page of the typed component tree (sections, groups, rows, calculations), each with its mappings, description, and status; cursor for the next page
get_values
readengineactive

The small-slice numeric read. Computed values for a {rows × periods} window, from any source: latest forecast, actuals, prior year, or a saved version.

in
rows; period range; source; basis
out
resolved values (tabular); never the full model
get_formula
readengineactive

The formula text behind a cell or row, with its references resolved across the sheet (!) and container (.) path. The raw material for explaining forecast logic.

in
cell, or row over a period range; source; basis
out
formula text; the rows/calculations each reference resolves to; per-period formula changes (a row can differ month to month; a calculation doesn't)
inspect_journal_entries
readengineboundedactive

The Inspect panel as a tool: the individual journal entries behind any actuals value — date, description, amount, source account — for a row over a period range.

in
row; period range; page cursor
out
a capped page of journal entries from the mapped accounts, with the contributing GL accounts; cursor for the next page
list_accounts
readengineboundedactive

GL accounts for a model with their mapping status — mapped (and to which row), unmapped-but-active, or unused. Resolves both "exists in e-conomic but not Francis" (unmapped) and the quieter case where an account is mapped but tucked away on a row the user has forgotten about. Always bounded, never dumped: a model can carry thousands of accounts, and on a fresh model every active account is unmapped, so the result is counts (by entity and status) plus a capped, cursor-paged set of rows. Narrow further with a data-source scope, a status filter, or a direct lookup by number.

in
data source or model; status filter (default: unmapped active); optional account lookup (number or name); page cursor
out
counts by entity and status; a capped page of accounts (number, name, status, mapped-to row); cursor for the next page
list_sources
readengineactive

Every source available within a model: saved versions (e.g. "May Forecast", "2026 budget") alongside the built-in latest forecast, actuals, and prior year. The lookup that resolves a prompt's named source to one the other tools accept, and the home for each source's forecast start — the attribute that sets a forecast's actuals/forecast cutoff.

in
model
out
per source: identity, save timestamp, type (budget / forecast / built-in), forecast start (for forecast and budget sources)

Analytical & diagnostic engine

deterministic · returns a small slice or findings list

Math and integrity tests the LLM must never attempt itself. Each returns a compact, ordered result the model narrates.

compute_variance
readengineactive

Diff two sources across a row set and period range, ranked by absolute or percentage delta. The engine behind variance tables, surfaced as a query instead of a rendered table.

in
anchor source; baseline source; rows/scope; period range; rank mode (# / %)
out
ranked deltas (row, periods, anchor, baseline, diff)
trace_calc
readengineplanned

Walk the dependency tree for a target cell — every input component and its value at each node — so the LLM can explain why a forecast or budget figure is what it is, rather than guess.

in
target cell; source; depth; basis
out
dependency tree with node formulas and resolved input values
run_health_check
readengineplanned

The model health check (planned feature): the deterministic suite of automated tests over a model. Surfaces notifications and unassigned dimension values, and runs the BS integrity check (assets − liabilities − equity) and the CF cash-tie check (statement ending cash vs. GL cash) — per period and per sub-sheet, so an imbalance is localized to the entity that causes it. The agent's entry point for "what's wrong with this model," and the place it starts before walking a troubleshooting guide. Net-new feature; per-sub-sheet localization in particular — see §03.

in
scope (model / sheet / sub-sheet); optional check types; period range; basis
out
findings, each with type (notification, unassigned value, BS imbalance, CF mismatch), location (sheet / sub-sheet / period), and signed residual where numeric

Suggestion authoring

the only write path · zero AI on commit

Suggestions never mutate committed state. The agent verifies its own proposal by reading in pending basis before a human ever sees it. This surface is intentionally thin — three tools — because the complexity lives in the engine's pending-aware reads, not in the write surface.

suggest_values
suggestllmplanned

Propose formulas or hardcoded values for a {rows × periods} window in the forecast layer — a VAT roll-forward, a SaaS revenue driver, the CF FX-fix formulas. The engine validates syntax; the human approves the numbers.

in
target rows/periods; formula or value per cell; bundle id
out
pending value suggestions attached to the bundle
suggest_structure
suggestllmplanned

Propose structural operations: add a sheet, add sections/groups/rows/calculations, apply a breakdown, add a roll-up, or add a GL mapping. Operation-typed, so a "create a sheet for Veloton ApS" and "build a functional P&L" use the same primitive.

in
ordered ops (each typed: add_sheet, add_row, add_calculation, apply_breakdown, add_rollup, add_mapping …); bundle id
out
pending structural suggestions attached to the bundle
bundle_suggestions
suggestllmplanned

Open or extend a bundle — the unit of interdependent suggestions a human approves together, and the unit a pending read evaluates against. A new sheet, its mappings, and its FX rows belong in one bundle.

in
title; rationale; optional existing bundle id
out
bundle id (the overlay handle used by every pending read)

Direct edits

gated · immediate · bypasses approval by design

A deliberate, separately gated exception to "writes are suggestions." These mutate committed state with no approval step, so their availability is governed by a session mode the operator sets up front, not a choice the model makes per call: off by default, enabled only for a trusted principal. They mirror the suggestion pair, so the model reasons about the same value/structure split — but skip the bundle, the pending overlay, and the human review loop, which is exactly why they're gated apart. They target the live model (saved versions stay locked), and every direct edit is audit-logged.

write_values
writellmactive

Write formulas or values straight into the forecast layer of the live model — the same target as suggest_values, but committed immediately rather than queued for approval. For trusted, low-friction editing where a review step would only slow a known-good change.

in
target rows/periods; formula or value per cell
out
the committed change (audit-logged)
write_structure
writellmactive

Apply structural operations directly — add or edit sheets, sections, groups, rows, calculations, breakdowns, roll-ups, mappings — committed immediately. The operation-typed twin of suggest_structure, without the bundle or approval gate.

in
ordered ops (add_sheet, add_row, edit_row, apply_breakdown, add_mapping …)
out
the committed structural change (audit-logged)

Collaboration

comments · direct write, not a suggestion

Threads are how the agent and the team discuss the model in place. Reading them is context; writing one is a direct action — a comment annotates, it never changes a number, so it doesn't go through the suggestion path. Comments are also where a colleague reviews a bundle (see §05).

list_comments
readengineactive

Pull comment threads on the model — open or resolved, by cell, sheet, author, or mention. Lets the agent pick up an existing discussion before answering or proposing, and read review notes left on a suggestion bundle.

in
scope (cell / sheet / bundle); filters (open, resolved, mine, mentions me)
out
threads with author, timestamp, anchor cell, resolved state
write_comment
writellmactive

Post a new thread, reply, mention a teammate, or resolve a thread — anchored to a cell, a sheet, or a suggestion bundle. The agent uses this to leave its rationale next to a proposal or to answer a colleague's review note. Mirrors the user's permissions.

in
anchor (cell / sheet / bundle); body; optional @mentions; action (post / reply / resolve)
out
the created or updated thread

02 / Work backwards

Every prompt, mapped to the calls it fires

All 20 prompts, clustered by the job shape they share. For each: the tool sequence, what the engine computes, and what the LLM does with the slice.

A

Connection & data-source diagnostics

Why did the Xero connection for Veloton Ltd fail?

list_data_sources

Engine: returns the Veloton Ltd source's failure reason and its status-check run — no model structure needed. LLM: reads the reason (e.g. authorizing user deactivated, wrong company signed in) and explains the fix.

A red notification next to the Veloton ApS sheet — what does it mean?

run_health_check→get_model_tree

Engine: the health check first confirms what the badge flags — a notification or an unassigned dimension value; the breakdown configuration then reveals which value is unassigned and where it routes. LLM: explains what the badge means and what needs assigning. (A stale data source is the other candidate — list_data_sources rules it in or out.)

Account 6115 Overkurs exists in e-conomic but not Francis.

list_accounts→suggest_structure (add_mapping)

Engine: returns 6115 with its status — unmapped, or mapped to a row the user overlooked. LLM: if unmapped, explains it's unmapped (not missing) and proposes a mapping suggestion; if already mapped, points to where. The mapping is a structural suggestion, human-approved.

B

Lookups & "why is this number" explanations

Actuals revenue for Veloton ApS hardware sales in 2025.

get_model_tree→get_components→get_values

Engine: get_model_tree and get_components resolve the hardware-sales row on the Veloton ApS sheet; get_values returns its actuals-layer values across 2025. LLM: states the figure, optionally the monthly shape.

Why was Dec-25 actuals hardware sales for Veloton ApS 440,304?

get_model_tree→get_components→inspect_journal_entries

Engine: get_model_tree and get_components resolve the Veloton ApS hardware-sales row; inspect_journal_entries returns the journal entries behind that Dec-25 cell — dates, descriptions, amounts, accounts. LLM: narrates what makes up the 440,304.

Why is budgeted hardware sales 540,394 in Dec-26?

get_model_tree→get_components→get_formula→trace_calc

Engine: get_model_tree and get_components resolve the budgeted hardware-sales row; get_formula returns its Dec-26 forecast formula and trace_calc walks the dependency tree with input values. LLM: explains the driver chain producing 540,394.

Explain the Veloton ApS COGS forecast logic in the 2026 budget.

get_model_tree→get_components→get_formula→trace_calc

Engine: get_model_tree and get_components resolve the COGS row in the 2026 budget; get_formula returns its formula (e.g. "Revenue"[0] * "COGS %"[0]) and trace_calc its inputs. LLM: describes the method — driver-based, statistical, or hardcoded.

C

Variance & source comparison

Biggest variances between May Forecast and actuals after closing June 2026.

list_sources→compute_variance

Engine: diffs the saved "May Forecast" version against actuals over closed months, ranked. LLM: narrates the top movers and likely drivers. Feasible from variance groups + saved versions.

Which OPEX item grows most, Budget-2026 vs Actuals-2025?

list_sources→compute_variance

Engine: resolves the Budget-2026 and Actuals-2025 sources, then diffs them across OPEX rows, ranked by growth. LLM: reports the largest and the percentage.

D

Statement checks & imbalance hunting

These start at the model health check, which surfaces and localizes the failing check deterministically. The agent then works the documented troubleshooting guide step by step — each step in the guide maps to a read tool, so the agent calls one per step until it finds the cause.

BS doesn't match for Veloton ApS actuals Dec-2025.

run_health_check (BS, sub-sheet)→get_components→get_formula→inspect_journal_entries

Engine: the health check returns the residual on that sub-sheet for Dec-25; the read tools then return mappings, formulas, and journal detail on demand. LLM: walks the BS troubleshooting guide in order — P&L/BS mapping, manual overrides, wrong-side mappings — calling the matching tool at each step.

Consolidated BS check won't zero — identify which entities/sub-sheets cause it.

run_health_check (BS, per sub-sheet)→get_components

Engine: the health check runs the BS test per sub-sheet and ranks residuals — this is the localization. LLM: names the offending entities, then drills into each via the guide. Per-sub-sheet localization is part of the planned health check, not in today's binary check (§03).

CF doesn't match for Veloton ApS actuals Dec-2025.

run_health_check (CF)→get_formula→inspect_journal_entries

Engine: the health check returns the cash-tie residual (statement ending cash vs. GL cash); read tools return the derived movement formulas and journal entries. LLM: walks the CF troubleshooting guide step by step, calling a tool per step, to find which movement breaks the tie.

E

Structural builds (suggestions, verified in pending basis)

Create a sheet for new data source Veloton ApS in our group structure.

bundle_suggestions→get_model_tree→suggest_structure (add_sheet + breakdown binding + mappings)→run_health_check (basis: pending)

Engine: projects the new sub-sheet under the breakdown, routes its actuals, recomputes the consolidated roll-up. LLM: proposes the bundle and confirms the group still balances before a human sees it.

Forecast 2026 VAT on Veloton ApS BS liabilities.

get_components→suggest_structure (supporting rows)→suggest_values (capture + settlement formulas)→get_values (pending)

Engine: validates and computes the roll-forward ("VAT payable"[-1] + sales VAT − cost VAT − settlement) with pending rows applied. LLM: builds the driver-based VAT structure and the settlement cadence.

Replicate the FX conversion (AVG for P&L/CF, closing for BS, plus CF FX-adjustment lines) across all sheets, using FR as reference.

get_components (FR)→get_formula (FR FX rows)→suggest_structure + suggest_values (per target sheet)→run_health_check (pending)

Engine: resolves FR's FX rows, projects the copied rows onto each target sheet, recomputes. LLM: reads FR as the template and emits per-sheet suggestions. No "use sheet X as reference" primitive exists — the agent reads FR and re-emits; structure-deploy is otherwise a breakdown behavior (§03).

Build a functional P&L (S&M / R&D / Admin) pulling department data from the nature-based P&Ls.

get_model_tree→get_components→suggest_structure (new sheet + calc rows referencing dept sub-sheets)→get_values (pending)

Engine: resolves cross-sheet (!) references from department sub-sheets and computes the functional view. LLM: designs the S&M/R&D/Admin mapping. No documented functional-P&L template; this is a modeling pattern, not a new tool.

Implement the documented CF FX fix after converting Veloton Ltd GBP→DKK.

get_components→suggest_structure (2 retained-earnings calc rows)→suggest_values (RE-start & RE-addition delta formulas)→run_health_check (CF, pending)

Engine: computes the two delta rows ("Retained earnings"[-1]/closing[-1]*closing[0] − [-1] and the avg-vs-closing net-profit delta) and re-checks the CF tie. LLM: authors the documented two-row fix and verifies it zeroes before proposing.

Plan and implement a SaaS revenue forecast across SKU categories.

get_model_tree→suggest_structure (line-item breakdown by SKU + driver rows)→suggest_values (predict / driver formulas)→get_values (pending)

Engine: projects the SKU breakdown and computes the driver build. LLM: plans the category split and per-SKU drivers, then verifies the roll-up.

Reporting & dashboards

Engine: the variance and value slices the report stands on. LLM: writes the exec summary and commentary as text components and lays out the dashboard. A report is a dashboard — a structural suggestion plus narrated text.

Actuals-vs-budget P&L dashboard.

03 / Gaps

Where the docs give no reason to assume a capability

Flagged as net-new rather than invented. Two were called out explicitly; both verdicts below are grounded in what the validation and variance docs actually describe.

net-new

Imbalance localization (BS / CF) — which entity broke the check

The BS validation is a single row (assets − liabilities − equity, summed per period) returning a binary zero/non-zero. The CF check compares statement ending cash to the GL cash account, also binary. Both ship with manual troubleshooting checklists; intercompany reconciliation is a manual per-pair difference formula. Nothing in the docs attributes a residual to a specific entity or sub-sheet.

It is, however, computable: the engine holds per-sub-sheet values, so the check can run independently per sub-sheet and rank residuals. This is slated to live inside the model health check feature (run_health_check) — the deterministic home for these tests — and is the capability behind cluster D's hardest prompt. Net-new; don't assume it exists today.

feasible

Source-pair variance

Documented directly. Variance groups compare any two sources — saved versions, latest forecast, actuals, prior year — with diff columns (#, index, %) and a baseline. compute_variance is a thin engine wrapper that returns a ranked slice instead of rendering a table. The "after closing June 2026" framing is just the last-close marker gating which months count as actuals.

net-new

The entire suggestion / pending / approval substrate

The docs describe comments, threads, and To-do/In-progress/Done statuses — but no draft, pending-change, review, or approval workflow, and saved versions are immutable snapshots, not a scratch layer. The whole suggestion architecture, including the human commit path, is new build. Expected, since it's the thing being designed — flagged so it isn't mistaken for an existing primitive.

net-new

"Use sheet X as reference" replication

There is no documented primitive for "replicate this sheet's structure onto others using FR as a reference." The one structure-deployment mechanism Francis describes is the breakdown (parent template syncs top-down to sub-sheets) — which doesn't fit ad-hoc cross-sheet replication. So the FX-replication prompt is served by the agent reading FR and re-emitting per-sheet suggestions, not by a replicate primitive. Fine, but it means N sheets = N suggestion sets, bundled.

net-new

Functional P&L template

The docs only describe departments as a cost-centre dimension scoped to OPEX. A functional S&M / R&D / Admin P&L that pulls department data across sub-sheets is a modeling pattern the agent constructs from cross-sheet formulas — not a missing tool. Feasible with existing formula syntax; just undocumented as a pattern.

04 / The central engineering requirement

Structural pending-state: reading the model as if a bundle were applied

Every structural prompt in cluster E depends on this. The agent must verify a proposed structure — that FX rows reconcile, that the CF tie zeroes, that the consolidated BS still balances — before a human reviews it. That means reads must evaluate committed state plus a pending bundle, and the bundle can change the model's shape, not just its cell values.

  1. An overlay evaluation mode, not a write

    The engine takes the committed model graph plus a bundle's ordered, uncommitted operations and produces a projected computation — without touching committed state. The bundle id is the overlay handle every basis: pending read passes in.

  2. Operations are DDL-like, not just cell edits

    The overlay must replay add_sheet, add_row, add_calculation, add_group/section, apply_breakdown, add_rollup, and add_mapping — plus edits and deletes — so a "new sheet" or "new breakdown" projects correctly, not only pending values on existing cells.

  3. Re-run the behaviors that structure triggers

    Adding structure cascades: a breakdown deploys the parent template top-down into new sub-sheets and re-routes actuals by mapping; a new mapping changes which journal entries land on which row; parent rows become read-only roll-ups of new sub-rows. The overlay must reproduce all of this, not just append nodes.

  4. Resolve new cross-sheet and cross-layer references

    Pending formulas use the same path grammar — sheet !, container ., relative offsets, fill-right, separate actuals/forecast layers. A pending FX row on Sheet B referencing a pending row on Sheet A must resolve within the overlay. This is what lets the agent assert "with my two CF-FX rows applied, the cash-tie residual is 0."

  5. The bundle is the consistency unit

    Interdependent suggestions — new sheet + its mappings + its FX rows — must be evaluated and approved together, because none reconciles alone. bundle_suggestions defines that unit; the overlay evaluates exactly that set.

  6. Evaluate against a chosen base source

    The overlay applies on top of a selectable base — the latest forecast, or a specific saved version. So a bundle's calculations can be previewed in the context that matters: a reviewer opens it and sees its effect "in the 2026 budget", not only against live. This is the hinge between pending state and the human review loop in §05.

What the docs say is — and isn't — already there

FOR feasibility  Francis already recomputes the whole model deterministically, resolves cross-sheet and cross-layer references, deploys breakdown templates top-down, and routes actuals by mapping. The computational machinery the overlay needs exists.

NOT YET THERE  Nothing in the docs describes a non-committed evaluation mode. Saved versions are locked snapshots, and there is no draft/pending/approval concept anywhere. The overlay engine — committed graph + bundle ops, evaluated without commit — is net-new, and it is the hardest single thing in this design.

05 / The shareable concept

The review loop: bundles, pending state, and comments together

This is the one idea that hasn't been socialized yet, and it's worth leading with for anyone seeing this cold. Three primitives already in this design combine into a single human-review surface. None of them is interesting alone; together they're how a colleague reviews and approves what an agent proposes.

How it reads to a reviewer

1. The agent groups its proposal into a bundle. A SaaS revenue build, or the CF FX fix, arrives as one set of interdependent suggestions — not a scatter of cell edits.

2. The bundle is evaluated in pending state, against a chosen source. Open it "in the 2026 budget" and the engine shows the calculations as if applied — the new rows compute, the BS still balances, the CF tie zeroes — without anything being committed.

3. Colleagues discuss it in place with comments. A reviewer leaves a thread on a specific suggested cell, mentions a teammate, and the agent can reply with its rationale. The thread is anchored to the bundle, so the conversation travels with the proposal.

4. A human approves the bundle. The commit path contains zero AI. Approval turns the previewed calculations into committed state, in the source the reviewer was looking at.

The thing to land with colleagues: seeing a calculation's effect before committing it is not a preview feature bolted on at the end — it's the substrate. The same overlay engine that lets the agent self-verify a proposal (§04) is what lets a human review one. Build it once and both audiences are served. The source-context selection (§04, point 06) is what makes it review-grade: people reason about changes inside a named source, not against an abstract "live" model.

How to share this

The page itself is the artifact to circulate — it's a default-private link you can share with teammates from the artifact's share control, and it stands alone for someone with no prior context. If you want a cut pitched specifically at the reviewer audience rather than the tool-builder audience, say so and I'll cut a shorter companion that leads with this section and drops the per-tool detail.

06 / Design considerations

The thinking behind the choices

The questions that shaped this taxonomy, distilled into the decisions they produced and why. This is the rationale a colleague needs to evaluate, defend, or extend the design.

Work backwards from prompts, but name tools above the prompt

The taxonomy is the union of calls the 20 prompts demand — yet tools are named one level of abstraction above any single prompt, so many prompts reuse the same few tools. Naming at the prompt level (a diagnose_connection here, an explain_forecast there) would have produced a sprawl of one-off verbs; naming at the capability level keeps the surface small and composable.

A tool is the unit of selection, authorization, and observability at once

Granularity was chosen where those three agree. When they conflict, the safety boundary wins, because the whole architecture rests on writes being approvable and the external caller being read-only. That is why read, suggest, and write are hard tool boundaries rather than modes of one tool.

Split reads by payload; merge writes by lifecycle

Structure is two tools to read — the whole-model map (get_model_tree) versus one sheet's contents (get_components) — because the binding constraint is payload size. Structure is one tool to write (suggest_structure, operation-typed) because the binding constraint is a shared approval lifecycle and the fact that related edits compose into a single proposal. The dominant force flips between reading and writing.

The verb prefix predicts behavior

list_ returns a collection, get_ a scoped single read, suggest_ an approval-gated write, write_ an immediate one. Consistent prefixes act as a selection signal for the model and a prior on the return shape, which measurably improves tool-use accuracy — so we standardized them rather than letting synonyms like read_ and get_ drift.

A tool's class is its lifecycle, not its payload

Effect on state is read, suggest, or write. Whether a write touches a value or a structure is a payload detail the tool name carries (suggest_values vs suggest_structure), not a separate class. By the same logic a comment is a write — immediate, annotation-only — not a suggestion, and routing it through the approval queue would miscategorize it.

Suggestions and pending reads are one mechanism — a git model

Committed state is main, a bundle of suggestions is an unmerged branch, reading with basis: pending(bundleId) is checking that branch out, and human approval is the merge. The payoff is that one overlay engine serves both the agent verifying its own work and a human previewing it. It is harder than git because the diffs are structural (closer to a database migration than a text patch), recompute isn't free, and committed state drifts under an open bundle — so bundles stay atomic and carry a base.

Pending verification is deterministic, and that is what makes suggestions trustworthy

Before handing off, the agent reads in pending and asks the engine — not itself — whether the balance sheet still balances and the cash flow still ties. So a human reviews a verified proposal rather than a plausible guess. The same pending surface is also where the agent builds interdependent, multi-step structures in the first place, since each step can see the computed effect of the last.

The engine computes; the LLM narrates; never the whole model

Reconciliation, variance, and integrity checks are deterministic engine work that returns a small slice. The LLM decides what to call, sequences calls, and turns the slice into prose — it never does the arithmetic, because the moment it does, the correctness guarantee is gone.

The read model is traversal, not similarity search

Reads form a drill-down ladder: orient (sources), map (the model tree), one sheet (components), a cell (values, formula, journal entries), then its dependencies (trace). Each step returns a bounded slice, and the agent navigates the model's deterministic structure to the exact node — keeping its high-level orientation the whole way, so an answer arrives grounded in its path (Veloton ApS → hardware sales → Dec-25) and is explainable. The deliberately rejected alternative is embedding similarity plus the model guessing which row is the right one, which would reintroduce exactly the non-determinism the architecture exists to prevent. Search is not absent — but it is deterministic and engine-ranked (biggest variances, failing checks, an account by number), and the agent traverses from those hits rather than from a fuzzy match.

Every read over a large collection is bounded

Accounts, journal entries, and large breakdowns return counts plus a capped, cursor-paged slice. A smart default is not enough — a fresh model has every account unmapped, and a breakdown can carry 100+ values — so the bound is a hard cap with a cursor, while summary counts carry the overview. The full collection never lands in the model's context.

Designed against a real large-client structure

The model tree was pressure-tested against a representative large client: three parallel breakdown hierarchies — functional P&L, nature-based P&L, and BS + CF — over eight legal entities, plus standalone sheets. Two facts shaped the bounding. Entity assignments are sparse, since a sheet almost always holds a single entity, so the entity layer never fans out. And department dimensions, though they carry hundreds of values, are manually grouped onto sheets — most sheets hold one to five departments while a catch-all "other" sheet absorbs the long tail. So the sheet hierarchy stays human-scale and is returned whole; the only large lists are the per-sheet dimension-value assignments, which is why those are summarized by count and expanded on demand.

Source is the umbrella, and it carries more than it appears

Sources are saved versions plus the built-ins: latest forecast, actuals, and prior year. Picking a source determines the layer, so there is no separate layer argument. And because structure and forecast start differ across sources, every structural read is parameterized by source.

Each fact at its native scope; the narrowest identifier implies the rest; defaults come from context

A connection is workspace-level, but which sub-sheet it feeds is model-level, so the binding lives in the model tree, not on the connection. A sheet identifier implies its model. And the location the user is prompting from — a model, a sheet, a date range — seeds the defaults, so the tool inputs never restate them.

Deterministic diagnostics live in the model health check; the agent then walks the guide

Balance-sheet and cash-flow integrity, notifications, unassigned values, and per-sub-sheet imbalance localization are engine work surfaced by one check. The agent calls it to find where something is wrong, then works the documented troubleshooting guide step by step — one read tool per step — rather than guessing at causes.

The scope lines are deliberate: admin out, direct edit gated

Inviting members and setting roles are not model edits, so they are descoped from v1 and the agent simply explains the manual path. Direct edit is an opt-in session mode, off by default and audit-logged, that consciously amends the "zero AI on the commit path" rule for trusted operators — chosen up front, not per call, so the human keeps the authority.

This is a design reference, and some of it is net-new

These descriptions are written for humans; the runtime tool schemas the model reads are a separate, derived artifact that strips the rationale and ships only what is built. And several capabilities — the entire pending/suggestion substrate and per-sub-sheet imbalance localization among them — are net-new engineering, flagged here so they are not mistaken for primitives that already exist.
